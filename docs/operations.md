# Operator procedure — future separate authorisation required

This procedure is documentation, not authorisation to execute a production operation. The local candidate has not deployed, funded, staked, installed authority, proposed, transferred, changed a controller or pushed anything on mainnet.

1. Close every mandatory gate in the acceptance matrix and retain the exact source commit, source/configuration manifests, raw Wasm, Candid, checksums, SBOM, security findings and two-build evidence. Verify actual remote CI run IDs after a separately authorised push. Require branch checks; workflow files do not establish protection.
2. Reserve the intended automation canister principal and review its controller/upgrade governance. Independently verify D-QUORUM neuron ID `4713806069430754115`, its expected controller, Governance's NNS Root controller, public read support and deployed API compatibility. Do not substitute a convenient test target or controller. No self-controller or rescue handoff is implied.
3. Install the exact canonical Wasm with `(opt record { mode=variant { ObserveOnly }; expected_target_controller=opt principal "REVIEWED_CONTROLLER" })`. Omitting the argument also selects observe-only, but then a fresh reviewed configuration is needed before write modes can be used. Read `configuration`, `scan_progress`, candidate/score/roster pages and `health`. Observe-only cannot apply following, claim a proposer, propose maturity or transfer ICP. Consequently it cannot publish a financially usable applied roster merely by observing one.
4. Separately authorise bootstrap mode through an upgrade argument `(opt variant { BootstrapInactive })`. Fund only the deterministic proposer staking account returned by `configuration`; never its default staged reward account. Verify the exact Governance owner, nonce and subaccount. The canister may claim/refresh only that account. Inspect the recorded proposer ID, controller and empty management following. The bootstrap mode does not apply rosters, submit maturity proposals or send rewards.
5. Through separately authorised NNS/controller operations, add that exact proposer neuron to D-QUORUM's management set and this automation principal as a hotkey. Do not remove other managers or assume sole management. Separately clear D-QUORUM CatchAll. Verify each result. Fund proposal fees through the proposer neuron's resources, independently of rewards.
6. Observe a complete scan and review exact scaled scores, positive/empty topic selections, manager overlap exclusions, freshness and candidate evidence. No partial scan is a valid ranking. Review the provisional equal-share policy and actual staking accounts. Review the first intended financial obligations under an authorised staged local rehearsal. A real first payout plan requires a fully reconciled applied roster; observe/bootstrap modes cannot manufacture that state.
7. Separately authorise live mode through an upgrade argument `(opt variant { Live })`. This authorises all implemented scheduled following/proposal/payment operations under the fixed policy; it is not a per-proposal vote from other managers. There is no runtime administrative activation endpoint. Review whether this all-at-once activation boundary is acceptable before deployment. Observe every first write, applied readback, proposal ID, other-manager decision, seven-day finalization, actual mint, immutable payout and Ledger confirmations.

If any authority is missing, the relevant job waits with a bounded error. Do not add a generic command endpoint to bypass it. Use `set_delegates_per_topic` only from actual NNS Governance; controllers are rejected. Changing count starts a new complete selection round and never rebuilds active payouts.

To halt new effects during an incident, a separately authorised upgrade to ObserveOnly preserves existing plans and evidence. A call already dispatched may still execute; reconcile it before any further operation. A code upgrade preserves active liabilities, proposal ambiguity and scan cursors. It does not turn missing history into absence. Never reinstall, clear a pending plan, replace a memo/timestamp or redistribute a partly paid balance.

BadFee and unresolved expired transfers deliberately hold the existing plan. This tranche has no operator override or arbitrary safe-retry endpoint. Further typed recovery code may be required for permanent history unavailability or a fee change; preserve all obligations and obtain a separate code review before an upgrade that changes recovery behavior. Incoming unsolicited deposits are future reward funding, not authority to alter recipients.

Use icp-cli with the reviewed `icp.yaml` and canonical artifact; no dfx project is supplied. No production command is embedded in the test/release scripts. The file's prebuilt checksum must match the retained canonical release before a future installation.

The successor hardening tranche changes eligible-voter scoring and stable schema V2; see [the hardening contracts](hardening-design.md). Historical RC1 behavior and hashes are not qualification evidence for this successor. Existing deployments must review migration to ObserveOnly, current observations and separate cache-maintenance status before authorizing live operation.
